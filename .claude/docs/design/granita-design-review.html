§2 a  ·  FOUR NAMES, ONE ROW

Two tiers, and the font carries it

The reader does not need to know which of four fields won. They need to know one thing: can I trust this string to tell me what the agent did? An alias can. A session summary can. A branch name usually can. bridge-cse_01W9sY8PbT2Du1dFGeYGcwWo never can. So there are two tiers, not four.

Recommendation. Render the fallback tier in .monospaced and tail-truncate it — the opposite of the Mac list in §1d, and for the opposite reason. A Bonjour name differs at its end, so the end has to survive; a generated directory name is bridge-cse followed by a ULID, and the ULID is noise while bridge-cse is the only mnemonic in the string. So the front survives here. Everything else stays proportional. Monospace says “machine string, there is no meaning in here” without spending a colour, and it is already this app's word for code. One font-design switch encodes the whole question. No glyph, no badge, no accent.

Alias against suggestion needs nothing at all: they are different kinds of string and read as such. “TLS pinning” is a title. “Make the diff scroll never reflow above the reader's finger” is a sentence. Nobody will mistake one for the other, and a badge distinguishing them would be answering a question no reader has.

Truncate the suggestion in the view, not on the wire. Keep the server's 60 characters — the rename sheet prefills with them and wants all of it. Display it at .lineLimit(2), which at 390pt is about 44 characters of headline. Two lines is the ceiling because three makes a 90pt row and a list of five of those is a wall of prose.

Rejected. An SF Symbol per source — four glyphs to learn, three of which are noise. Italics for suggestions: in a list, italic reads as an error or a placeholder. Showing the directory name as a second line under a branch name: it is the one string the reader never wants, given twice the space of the one they do.

Should feel like a list of things people named, with the occasional machine string that visibly did not get named. The unnamed ones should feel slightly unfinished, because they are.

§2 b, f  ·  PINS AND FLAGS

Pinned section: confirmed, with one addition

A single Pinned section above the project sections is right, and the objection is real — a worktree does appear away from its siblings. The fix is one field, not a different structure: a pinned row keeps its project name on line two even in grouped mode. Then it is not orphaned, it is annotated, and the reader can see it belongs to granita while sitting above granita. Look at the two frames above: the pinned row is the only one in grouped mode carrying a project name, and that difference is the explanation.

Rejected. Floating a pin to the top of its own project section — you still have to find the project, which is the work the pin exists to skip. And duplicating the row in both places: a row that appears twice is a worse bug than a row that appears once in a surprising place.

Because the section carries the pin, no pin glyph on the row in grouped mode. Flat mode has no header to carry it, so there the pin appears as a leading pin.fill at .caption2, secondary. One or the other, never both.

Of the four git flags, one and a half earn pixels

isPrimary earns a word. “Primary checkout” on line two is exactly the reader's own mental model: this is the one the agent did not work in. It also explains why that row usually has no changes, which is otherwise the most confusing row in the list.

isDetached earns a word conditionally — only when displayName fell through to the directory name. Then it is not a flag, it is the answer to “why is this row a random string?”. When there is an alias, detachment is irrelevant to reading a diff and stays off.

hasUnbornHead earns the stats slot, not a flag: “no commits yet” where +n −m would be. Everything compares against the empty tree, so the real numbers are the whole repository and they are a lie about what changed.

isLocked earns nothing, ever. It is git plumbing with no bearing on reading a diff, and v1 cannot prune worktrees, which is the only operation it would block.

Should feel like the row is telling you how long this will take and how fresh it is, and nothing else.

§2 c  ·  WHICH CONTROL

Not a segmented Picker. A toolbar Menu.

This is the “which system control” answer, and it is the strongest single recommendation in section two.

A segmented Picker is a permanent 32pt band at the top of the list, plus its own 16pt of padding — 48pt of every scroll, forever, spent on a preference that is set once and then never touched again. It also lands directly above the “Pinned” section header, so the first thing the reader sees is two rows of chrome before any content.

Recommendation. One toolbar Menu holding a Picker with .pickerStyle(.inline) — the mode stays a Picker in code, and the two options render as checkable rows. The clincher is that there is a third preference (open call 3, below) and probably a fourth, and three toggles cannot be three segmented controls, but they are three menu rows without a redesign. On iPad the same menu sits in the sidebar's toolbar.

And yes — flat mode promotes the project name. It moves onto line two ahead of the file count, where the section header used to be. That is the one field the list cannot lose, because without it a flat list of agent sentences has no idea what codebase it is talking about.

Rejected. Sections in a .searchable scope bar — a scope bar filters, and this does not filter. A leading-edge sidebar toggle button: two states with no labels, so the reader has to press it to learn what it does.

Should feel like Mail's sort menu. You touch it in week one and then forget it exists.

§2 d  ·  THE RENAME SHEET

The footer previews the result, so “clear” needs no explaining

One .sheet at .presentationDetents([.medium]), a NavigationStack inside it, Cancel and Save. Nothing here is a new control.

The one idea worth keeping. The section footer always states what the row will read after Save, and it updates live as the field changes. That single sentence answers all three of your cases at once. An empty field is not a mystery — the footer says “will show as feat/tls-pinning”. The placeholder is the derived name, so an empty field even looks like the fallback it will produce.

Clearing an alias needs no destructive button. The field's clear glyph plus Save is the whole gesture, and the footer confirms it before the tap. A red “Remove alias” row would put a destructive treatment on an operation that touches no git state and is reversible in four seconds.

Do not prefill with the suggestion. The specification says prefilled; I would offer it instead. A prefilled field means the reader's first act is to select-all and delete 51 characters on a phone keyboard, and it hides the difference between “I accepted the agent's summary” and “I named this”. Offering it as a tappable row costs one tap for the accept case and saves the delete for every other case. The row shows the suggestion at full length — two lines if it needs them — because this is the only place in the app where all 60 characters are worth reading.

With no suggestion, the section is absent and the footer says why in the reader's terms: no session, or detached, or both. That turns an empty sheet into an explanation.

Rejected. An .alert with a text field — it cannot hold a two-line suggestion, cannot show a live footer, and gets clipped by the keyboard. A full-screen push: renaming is a four-second job and does not deserve a navigation event.

Should feel like renaming a photo album. You are never unsure what will be on the row when you let go.

§2 e  ·  STATES  +  OPEN CALL 3

Hide the quiet ones, and say how many you hid

Recommendation for open call 3. Hide worktrees with no changes by default, and put the count in the list's footer as a tappable line: “6 worktrees with no changes are hidden. Show them.” — visible in the grouped frame above. That kills your own objection: the list now states what it is hiding, so the number in the menu bar and the number on the phone reconcile on screen instead of contradicting each other silently. The permanent version of the same switch lives in the toolbar menu.

Rejected. Showing them dimmed — dimming reads as disabled, and a reader who taps a dimmed row and gets a working screen learns to distrust dimming everywhere else in the app. Showing them in a collapsed “Quiet” section: a section header per project plus a Quiet section per project is more chrome than content on a slow day.

The four states, briefly

No projects enabled. A ContentUnavailableView with no action, because there is nothing on this device to tap. The description names the exact menu — “Granita's menu bar item, under Projects” — so the sentence is the instruction. A disabled button, or one that opens a “do this on your Mac” modal, would be a control that cannot act.

Enabled but all clean. Same control, and here the action is real: “Show them anyway” reveals the hidden clean worktrees. The count in the description is what makes this state trustworthy rather than alarming.

One project only. Not a special case. Leave grouped mode on and let the single section header be the project name — it costs 28pt once and it is the only place that name appears. Auto-switching to flat would make the list change shape when a second project is added, which is a worse surprise than a redundant header.

312 files beside zero. No treatment needed beyond writing “no changes” where the numbers would be. The numbers are already tabular and already coloured; a 312-file row is visually heavier than a clean one without any help, and that is the correct hierarchy — the big one is the one you came for.

Should feel like an inbox that has already thrown away the newsletters and told you it did.

§2  ·  IPAD

320pt makes the same row work harder, not differently

A NavigationSplitView sidebar is 320pt at this size class — narrower than the iPhone's 390. So the iPad is the harder layout for this row, not the easier one, and the drop order in the table above is what saves it: the 58-character suggestion goes to three lines at 320pt unless the line limit holds it at two, and the file count is the first thing the second line loses.

Two things the iPad gets for free by using the right control. NavigationLink draws no chevron in a sidebar and instead gives the selected row the tinted selection you can see on the second row — which is also the answer to §1's chevron. And the empty detail column is a ContentUnavailableView, the same control as every other empty state in the app.

Should feel like Mail with the mailbox list open. The sidebar is a place you look, not a place you work.

§3 a, b  +  OPEN CALL 1

Keep the sheet. Make it a drawer, not a modal.

Recommendation for open call 1. The selector earns its screen, but not as a modal. Add .presentationBackgroundInteraction(.enabled(upThrough: .medium)) and drop the dimming. Now the diff keeps scrolling behind the sheet, tapping a file jumps the scroll with the list still open, and the reader can walk a change set file by file without a dismiss-present cycle between each one. That is a materially different tool from the modal version, and it is one modifier.

Rejected: a jump-to-file Menu in the diff toolbar. It is cheaper and I nearly recommended it. It loses on three counts. A Menu cannot indent, so directory grouping — which you locked — cannot be expressed in it. It cannot scroll to 300 items usefully and cannot be searched. And it cannot show viewed across the whole set, which is the selector's second job and the only place the reader can see how much is left. A menu answers “jump”; it does not answer “where am I in this review”.

What survives on the row, in order

name → status → viewed → stats. The stats go first when width runs out, because the file header in the diff repeats them 200ms later. Then viewed collapses into the name going secondary — a dimmed filename already means “done” and needs no glyph. The floor is M ServerDiscoveryView.swift, and at 390pt inside a sheet at depth 3 that leaves about 200pt for the name, which is 24 characters. Most Swift filenames in this repository are longer than that, so the name head-truncates too: …DiscoveryViewSnapshotTests.swift.

The status letter and the viewed mark can share a row, but not an edge. Status leads, because it is part of the file's identity and it aligns into a column the eye can scan down. Viewed trails. Putting both on the trailing edge is exactly the two-checkboxes problem you predicted.

And the viewed mark is not a control in here. A 32pt row inside a sheet cannot hold two tap targets without generating mis-taps, and the row's job is to jump. It is a checkmark that reports state. The toggle lives in the diff's file header, where the reader is when they finish a file.

Should feel like the Photos album drawer: a thing you pull up, use, and leave up.

§3 c, d, e  ·  DIRECTORIES, FLAT, STATES

A directory aggregates only while it is shut

Yes to both halves of §3c, with a rule that keeps them from fighting. A collapsed directory carries the summed +n −m of everything inside it; an expanded one carries none, because its children are right there with their own numbers and the parent's total becomes noise you have to mentally subtract. Same for viewed: a checkmark on the directory when every descendant is viewed, at either state, because “this whole subtree is done” is the most useful thing the tree can tell you. Above roughly 20 children a directory arrives collapsed, which is what makes the 80-directory case readable.

§3d: same row, different label. Not a different design. The path splits into two runs in one Text: the directory prefix secondary at .footnote, the filename primary at .subheadline, head-truncated so the prefix erodes and the filename never does. The status column, the stats and the viewed mark are untouched, which is the point — one row implementation, two labels.

One changed file. No tree. At three files or fewer, or a single directory, render flat and do not offer the toggle — a tree over one file is two rows of ceremony for one row of content.

Over 1,000 files. A plain footer line, not an alert. The server already returns isTruncated and a reason; print the reason. Say “not served” rather than “load more”, because WorktreeLimits.standard will not serve them and a button that cannot succeed is worse than a sentence.

Everything viewed. Not a ContentUnavailableView — the files are still there and still openable. The list renders normally with every name secondary and every check set, and the footer says “All 12 files viewed”. The reader's next move is to leave, and the app should not congratulate them.

Should feel like the Xcode navigator, minus the parts of the Xcode navigator nobody uses on a phone.

§4 a  ·  THE FILE HEADER

Sticky, and it costs 28pt — but only if the toolbar goes

It has to stick. It is the only thing that answers “where am I” after thirty seconds of scrolling, and the alternative — reading the path off the nearest hunk heading — is not an answer because hunk headings are function names, which repeat.

Two forms, one header. In flow it is two lines: path, then status, stats, language and hunk count. Pinned it reduces to a single 28pt line — collapse chevron, status letter, head-truncated path, stats, viewed toggle. Nothing is lost that the reader needs while inside a file; the second line is orientation for arriving, not for staying.

Then the toolbar has to hide on scroll. Your arithmetic was right: sticky header plus gutter plus toolbar is most of a phone. Sticky header alone is 28pt of 844, or 3%. So .toolbarVisibility(.hidden, for: .navigationBar) while scrolling down, restored on scroll up — and the Files button comes back with it. The frame is drawn with the toolbar gone, because that is the state the reader is in 95% of the time.

Implementation that keeps your no-reflow rule intact: one Section per file in a LazyVStack(pinnedViews: .sectionHeaders). Pinning is a rendering position, not a layout change, so nothing above the finger moves.

Rejected. Putting the path in the navigation title and updating it as files pass — it fights the toolbar-hiding above, and a title that changes while you scroll is the single most reflow-feeling thing you can do to a reader even when nothing reflows. Also rejected: a floating path chip. It is a sticky header that has given up its collapse control and its stats.

One gutter column on the phone. Both on iPad.

SF Mono at 11pt advances 6.6pt per character. A four-digit number is 26.4pt; with 9pt of trailing space and 4pt of leading inset, one column is 39pt and two are 78pt. At 390pt with a 12pt trailing inset, that is 51 characters of code with one column and 41 with two. Neither reaches 80, which is the honest headline of this whole section — but 41 is not a diff viewer, it is a keyhole.

Keep the new number. The reader is reading the current state of the file and will go looking for line N in the working copy; the old number is only useful for talking to someone about the previous state, which v1 cannot do — there are no comments and no export. On a deletion row the column is blank, and the row tint already says which side it is. Width is computed per file from its own maximum line number, so a 200-line file gets a 3-digit gutter and 8 more characters of code.

Rejected. A single interleaved column showing whichever number exists — it looks like one sequence and is two, so scanning it produces wrong line numbers with total confidence. And shrinking to 10pt to fit two columns: 57 characters, and code you have to squint at, which is the opposite of the product's purpose.

Should feel like reading code in Xcode with the navigator shut. The gutter is furniture; the code is the room.

§4 c, d, e, f  ·  TINTS, BARS, EXPANSION, EDGES

In dark mode the segment is carried by the text

“Stronger” is a ratio, not a colour. Row tint at 10% of the semantic green or red; segment at 28%. Below about 3× the segment stops being a second layer and becomes a slightly damp patch — and in dark mode, where the base tint has to sit at 16% just to be visible against black, there is no headroom left above it. Two nested backgrounds is the premise that does not survive dark mode.

So invert the emphasis there. Unchanged runs on a changed line drop to .secondary; the changed run goes to full-strength label. The eye finds the bright text, not the darker box. It works in light too — the swatches above use it in all three palettes — and it is the only treatment that survives the colourblind palette, where orange on white is already low-contrast.

Rejected. Underlining the changed run — it collides with whatever the syntax highlighter does and disappears under a descender. Bold: SF Mono keeps its advance when bold, so it is technically safe, but bold already means “keyword” to anyone who reads code, and this repository highlights per side.

A collapsed bar must say why it is shut

44pt, and four things: status letter, head-truncated path, stats, and — the one you have not specified — the reason. “viewed 4 minutes ago”, “1,558 lines · Load diff”, “binary · no diff to show”, “renamed from SessionStore.swift · no content change”. Without the reason, the reader has to open a file to learn there was nothing in it, which is the exact cost collapsing was supposed to save. With it, a run of six bars is readable at a glance and three of the six never need opening.

A binary file and a rename-with-no-content-change get no chevron at all. There is nothing behind them, and a disclosure control that discloses nothing is the smallest possible lie.

Expansion lives on the trailing edge of the hunk header

The hunk header is already a full-width band at quaternarySystemFill carrying git's section heading — which is the most useful free string in the whole diff, and the reason the header does not read as content. Put the expand control at its trailing edge in a 44pt hit area. Not the leading edge: that is the gutter's column, and a glyph there reads as a line number. “Expand all” goes in the file header's Menu, not on screen — one visible expand control per hunk is already one per 20 rows.

Conflict markers get the orange row and the file gets a badge. They arrive as ordinary diff lines, so the parser's conflictMarker kind is the only thing that makes them findable — a full-width warning tint, the marker text at semibold, and CONFLICTED in the file header so the reader knows before they scroll. This is the one status worth a badge.

Should feel like a long page of code with signposts, where the signposts are quieter than the code.

Tapped. But put inference behind a menu item.

Recommendation. The tap is the only writer. This app has exactly one job — telling you whether you have read the code — and an inferred “viewed” that fires on a fast flick is the app lying about the only thing it is for. Content-hash keying makes a stale mark self-correcting, which is elegant; it does nothing about a mark that was wrong when it was written.

The middle ground is worth having, though, because scrolling past thirty small files and tapping thirty circles is real work: “Mark everything above as viewed” in the file header's menu. Inference on demand — the reader asserts it, so it is still their claim.

Rejected. Inference with an undo — undo on a state that was set silently is a control for a mistake the reader does not know they made. And a hybrid that infers only for files under 20 lines: two rules for one flag, and the reader cannot tell which one applied.

Cut focus mode on iPhone. Keep it on iPad, where it is free.

On iPad focus mode is not a feature, it is the third column — you get it by having a NavigationSplitView at all. It earns its existence there by costing nothing.

On iPhone it is a second reading surface with its own scroll state, its own gutter, its own previous/next chrome, and its own bugs — for a reader whose continuous scroll already has a collapse control and a file list one tap away. I would cut it from M5 and see whether anyone asks. If it does ship, it must not be the tap target on the file header: tapping a header with a chevron on it has to collapse the file, or the chevron is decoration. Focus mode belongs in that header's menu, drawn above as “Open on its own”.

Should feel like your own claim about your own reading. Nothing in this app should ever tell you that you read something you did not read.

What I could not decide from here

Two things need a real device and a real change set rather than another round of frames.

The code point size. Everything in §4 is measured at 11pt because that is what makes 51 characters fit. Whether 11pt is readable to you at arm's length on a 6.1″ screen is not a thing I can judge from a drawing, and it moves every number in that section. Set it on the device first, then let the gutter follow.

And whether wrap-off survives at all on the phone. I have argued that horizontal scroll is the primary interaction rather than a fallback, and I believe it — but a two-axis scroll inside a vertical scroll that must never reflow is the single hardest gesture in this product, and it is the one thing here that a frame genuinely cannot tell you. Build the wrap-off scroll first, before the collapsed bars and before focus mode. If it does not feel right, character wrapping becomes the default and half of §4b stops mattering.
